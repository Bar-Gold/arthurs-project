# CLAUDE.md: the Qt UI

The root `CLAUDE.md` applies here too; this file adds the rules specific to
`fbposter/qtui/`, the app's window. The general UI rules (only the main thread
touches widgets, the three permitted modals, closing the window, `body_for()`, the
injectable browser seams) stay in the root file under "UI rules", as do Hebrew,
invisible characters and the first-run wizard.

The Qt tests (`tests/test_qtui_*.py`) are in a directory this file does not cover, so
open it before editing one of them.

## The flow: what, then where, then when

Three steps, one road. Since 2026-10-19 (the user's request) they are the pages of one sidebar item, **Create a post** (`views/create.py`, `CreatePostView`), not three items of their own. A step bar at its top reads `1. Write the post`, `2. Choose the groups`, `3. Choose when`, marked with the setup checklist's drawn marks. **An earlier step can be clicked to go back; a later one is disabled**, so forward is only each step's own Next button and the order always holds (the user's choice). The step bar uses `#Step`, drawn like `#Tab` but never bold: bold is wider than the width the button was sized for, and cut "Choose the groups" short.

The pages are the same `ComposeView`, `GroupsView` and `PublishView`, built by `CreatePostView` and still registered in `App.views` under `compose`, `groups` and `publish`. **`App.show_view` routes a step's key into the flow** (`flow.go_to`), keeps `current_view` as the step's key, and lights "Create a post" through `NAV_PARENT`; `show_view("create")` goes back to whichever step the post was at. Each page's big title (`self.heading`) is hidden inside the flow under its one title; the one-line instruction stays.

**A post that went out or was queued starts a fresh one** (`CreatePostView.start_over`, called from `PublishView.publish` on success only): `ComposeView.clear_draft`, the selection cleared, `PublishView.reset_form`, the flow back on step 1, and the window on **Home** (`views/home.py`). A refused post keeps everything. Home is where the app opens once setup is done and where the wizard's last button lands: one headline, one line, and one `#Primary` button, Create a post, and nothing else (the user's choice: no numbers, no lists). It is the first sidebar item, and the logo at the top of the sidebar (`App.brand_button`, `#Brand`, drawn like the label it replaced) leads there too.

The split into what, where and when is load-bearing, not cosmetic:

- **Compose: what.** The text, the per-group rewrites, the attachments, the templates. No timing controls and no group picker; it shows a read-only "Sending to" summary and its primary button just navigates.
- **Groups: where.** The list fills itself once after the first login, and "Get my groups from Facebook" (`import_from_facebook`, enabled only while connected) reads it again; see "Reading the client's groups off Facebook" in the root file. After an account switch the next read replaces the list instead (`_replace_with_found`; root file, "Changing which Facebook account it posts as"). Ticking recipients and managing the list are one screen on purpose: the moment you notice a group is missing is the moment you are choosing groups, so the button lives there. There is no box for a group's link (removed 2026-10-14); a search box sits in its place. **A search hides rows, it never rebuilds them** (`apply_search`), and it is not in the snapshot, so typing costs no widget construction. Removed groups sit under the list behind "Show removed groups", each with "Bring back"; one brought back starts ticked. **A click anywhere on a group's row ticks it** (`GroupRow`, the user's request, 2026-10-14). The box and "Remove" keep their own clicks, and Qt passes every other click on the card up to the row; `test_qtui_groups.py::TestTheWholeRowTicks` clicks at real geometry. The member count sits muted on the right of the row, as Facebook wrote it, and is in the snapshot. **A row never shows the group's number**: until the name arrives it reads `LOOKING_UP`. Showing the number is the fallback only when the name cannot be read. Name lookups are *queued*, never dropped: a lookup asked for mid-sweep marks its rows `LOOKING_UP` at once and runs straight after, for only the groups that sweep did not try, so a name that cannot be read is never re-asked in a loop. A dropped request used to leave the number on screen until the Groups screen was reopened, which was reported as "about a minute". `App._on_check_result` also looks up nameless groups when the connection comes back `CONNECTED`, which is the first moment a group added while Chrome was starting can be named. `tests/test_qtui_group_names.py` pins all of it.
- **Group sets are picked on Groups, made on their own screen** (`views/group_sets.py`, a sidebar item below the Dashboard, not a step; the user's choice, 2026-10-15). The rules are in the root file under "Group sets". On Groups, a "Group sets" strip above the list has one box per set, hidden until a set exists. **The set boxes are rebuilt only when the sets change, never on a pick**: the box clicked would be destroyed under its own click. Whether each is picked is restated outside that guard, as `_mark_active_tab` does, because Clear changes it without a click. A group a picked set brings is drawn ticked and disabled with "in <set>" beside it, and the snapshot carries that, so picking a set redraws the rows. `GroupRow` checks `isEnabled()` before `toggle()`, which ignores a disabled box. The edit screen keeps `_own` (the ticks made by hand) so unticking a set gives each row its own tick back. The greyed tick is `QCheckBox::indicator:checked:disabled` in `theme.py`. The Group sets screen's editor is part of the same view, not a screen of its own; walking away and back leaves it open.
- **Publish: when.** Now, Once, or Repeat, in one card. It calls `ComposeView.add_to_queue(when)` for the first two. **`PublishView.on_show()` calls `compose.capture()` first**, because `body_for()` reads committed state only and would otherwise publish the text from before the user's last keystroke.

**The selection lives on the window, not in a view**: `App.selected_groups` (a set of ids) with `App.selected_group_ids()` deriving the ordered list from the live group list. Three screens need to agree on it: Groups ticks them, Compose opens a wording tab per group, Publish sends to them. Deriving the order rather than storing it means a group deleted while ticked simply drops out instead of surviving as an id that no longer resolves.

**Times are picked from two lists, never typed** (`TimePicker`: an hour list and a minute list, `TimeList`). The user found the typed field with arrows awkward to use and to change, and chose lists with minutes every quarter hour (`MINUTE_STEP`, 2026-10-14). It is used by Repeat, the repeating-post editor and Once. A saved time off the quarter (09:10, from before) is added to its list rather than moved, so editing a post never shifts it. The lists are a fixed `TIME_LIST_WIDTH`: Qt's own guess pushed the "When" column past the window's edge.

**The one-off picker is `ScheduleEntry`: a `DateEntry` above a `TimePicker`**, not a bare `QDateTimeEdit`. A stock one opens with the *year* section focused and accepts the mouse wheel, so one scroll over it moved a post a year out and two read as "the default is 2028", which is exactly how it was reported. The day starts on the day section, nothing in it takes the wheel, and it is bounded to `[now, now + SCHEDULE_HORIZON_DAYS]`: an hour or minute outside that is greyed in its list (`item:disabled` in `theme.py`), and a day picked with its time already gone moves to the first time left. It defaults to **the next quarter hour** (an arbitrary +1h offset was reported as the next thing to undo; the current minute is not on the list) and `reset()`s every time Once is opened rather than once at startup. A default set at launch is a past time by the afternoon.

**Days are shown Sunday to Saturday**, as the week runs in Israel (the user's choice, 2026-10-14): the day boxes (`publish.day_boxes`, shared with the editor), `recurrence.describe`, and the calendar's first column. Only the order shown changed. `_day_boxes` is still indexed by `datetime.weekday()`, 0 being Monday, because that is how every stored schedule records its days.
- **In Repeat mode the Compose text is wording #1**, and the screen collects *alternates*. That is what stops "which one is the real post?" being a question the user has to answer.
- **An existing repeating post is edited on its own screen** (`views/schedule_edit.py`), opened by the Edit button on its card. Loading it back into Compose, Groups and Publish was the alternative, and was turned down: those three hold the draft the user is writing next, and an edit must never cost them it. There, every wording is equal (there is no "Compose text"), and the wording boxes are a fixed height, because in one scrolling column expanding editors shared out the whole window and pushed Groups and Pictures out of sight.
- The three mode panels live in one `QStackedWidget`, and `set_mode` marks every page but the current one `QSizePolicy.Ignored`. A stacked widget is otherwise as tall as its tallest page, which left a large void under the one-line Now panel.
- Repeat-only widgets are grouped in `self.repeat_extras` and shown or hidden as one. Hiding them individually left their spacing behind and pushed the rest of the column down the screen.
- **The sidebar: Home, then Create a post, then a divider and the places you look afterwards.** Dashboard, Group sets and Posting tips, with Settings at the foot. An icon names each item. Compose, Groups and Publish were three numbered items ("1." to "3.") until icons replaced the numbers (2026-10-12), and three items until they became the steps of Create a post (2026-10-19). The Dashboard replaced the Queue (2026-10-14).
- **Settings sits at the foot of the sidebar, above the connection status, apart from the steps.** Three cards in a scroll area: the scheduler and its pause, the Facebook account switch, and "This PC" (start with Windows, keep awake). The posting-rules card (hours, daily limit, cooldown) went with the rules on 2026-10-18. It is laid out like system settings (2026-10-12): each setting is one row, its name and hint on the left and its control at the right (`SettingsView._setting`), with a hairline between rows and card titles one size up (`#CardTitle`). The two PC settings are `widgets.Switch`, drawn like the Windows 11 switch, because each takes effect the moment it is flipped; it is a `QCheckBox` underneath, so the code and tests treat it as one. A note with nothing to say is hidden, so it leaves no gap. The PC card asks Windows off the drawing thread and takes its checkboxes' state from the answer, never from the click. Pausing used to be a card in the sidebar on every screen; the user did not want the control that stops every post that close to hand. What stays in the sidebar is the *fact*: `App.paused_notice` ("Posting is paused", `#PausedNotice`) shows only while paused and leads to Settings. Its text goes plain on `:pressed`, because the warning colour is 4.15:1 on the pressed grey. `test_qtui_settings.py` has an autouse fixture detaching the stub worker before the window closes: with a worker attached and a batch waiting, `closeEvent` raises the real close dialog and the run hangs instead of failing.
- **The wording tabs live on their own row in a horizontal scroll area.** Sharing a row with the Write/Preview toggle, the layout shrank them below their own text and clipped group names mid-word once the font grew. The strip uses `setAlignment(Qt.AlignLeft)` rather than a trailing stretch, because `refresh_tabs()` clears the layout by index and counts what is in it.
- **A bare `QWidget` inside a card draws a grey band across it**. The global stylesheet gives every widget the window background. Use `widgets.row()` for any container inside a card; it is styled transparent in `theme.py`.

## Where am I, what just happened, and taking it back

Reviewed against Apple's design principles on 2026-10-12 (the `apple-design` skill). `tests/test_qtui_feedback.py` pins each of these.

- **The sidebar lights where you are, or nothing.** Screens outside the sidebar map through `NAV_PARENT`: the three steps and the repeating-post editor light Create a post, and the setup wizard lights nothing. An exclusive `QButtonGroup` refuses to leave nothing checked, so `show_view` switches exclusivity off around the update. Without that, the item clicked last stayed lit, often Settings.
- **Status is a banner (`widgets.StatusBanner`), never a dialog.** It used to be one line of small grey text that went after 4.5s, errors included. The kind of message is a coloured bar, a widget of its own. Drawn as the frame's left border, it bent round the rounded corner and read as a bracket. The words stay in the body colour, readable at every level. `message_duration` scales the time on screen with the length, up to 15s; an error stays until it is closed or replaced. The text is selectable so an error can be copied word for word. `App.toast_label` is still the message label, which the tests read.
- **Forgiveness, not "are you sure?".** Delete (repeating post), Cancel (batch) and Remove (group) each put an **Undo** on the banner, for at least 10s. `App.toast(..., undo=fn)`: `fn` puts it back and returns what to say, or `None` when it no longer can ("Too late to undo"). The restores are `ScheduleRepo.restore` (same id, so its past batches are its own again, with `run_count` and the next slot), `TaskRepo.uncancel`, and `GroupRepo.restore`. Each puts back only what is still as the action left it. This adds no modal, so the permitted-modal list stays at three.
- **A warning looks like a warning.** `widgets.set_note_lines(label, facts, warnings)` sets the facts in the label's own colour and the warnings in `WARNING`, one `<div>` each so every line keeps its own text direction. Text is escaped, because group names go into it. The Publish and repeating-post summaries use it.
- **Large type is tracked tighter.** `widgets.TRACKING`, about -0.02em, set by `AppStyle.polish` because a stylesheet cannot set letter spacing. The stylesheet's size and weight still apply on top.
- **No motion was added, on purpose.** The skill's springs, gesture physics and translucent materials are written for the web. A desktop window switching panes instantly is what people expect, and animation here would cost attention for nothing.

## Badges, joined toggles and icons

The second review against the `apple-design` skill (2026-10-12) made the window look finished. The user chose all four changes; `tests/test_qtui_look.py` pins them.

- **A status is a badge** (`widgets.badge`, `set_badge`): a tinted capsule, 13px semibold. It is used for every status on the Dashboard, a repeating post's Active or Paused, and the scheduler on Settings. Statuses still name a colour token (`TASK_LABELS`, `TARGET_LABELS`, `STATUS`), and `theme.BADGE_TINTS` gives the tint behind it. Each pair is in the contrast test; the first green tint read 4.41:1. As coloured words they were the size and weight of the grey Cancel and Delete beside them, so a status looked like a button. A badge never stretches: in a row it would grow to the row's height and read as a button again.
- **A two- or three-way choice is one joined toggle** (`widgets.segmented`): Write/Preview, Now/Once/Repeat, Recent/All. The chosen segment is raised in `SEGMENT_ON` out of a `SEGMENT_TRACK`. Its weight does not change when chosen, because bold is wider and the segments would shift under the pointer. The caller keeps its own exclusive `QButtonGroup`.
- **Icons are SVG strings in `qtui/icons.py`, drawn by Qt's SVG image plugin.** Not files: an SVG file cannot take a palette colour, and PyInstaller does not collect `.svg` on its own (see `packaging/CLAUDE.md`). Nothing imports `PySide6.QtSvg`. A sidebar icon is muted at rest and accent while its screen is open, because a checkable button draws its icon's On state when checked. Qt puts a fixed 4px between an icon and its label, so `NAV_ICON_BOX` draws the icon 8px wider than tall with the drawing at its left. Pixmaps are drawn at the screen's own scale.
- **The connection status is a drawn dot and words under a rule** at the foot of the sidebar, not a card. The setup checklist uses drawn marks too (`welcome.MARKS`): the typed tick, triangle and circle came out at three sizes and heights.
- **A heading is never smaller than what it heads.** `SectionHeading` is body size, semibold. At 13px, "Going out" sat above a list of names larger than itself. `theme.HEADER_GAP` (16px) separates a screen's subtitle from its content, and every view uses it.

## The Dashboard answers "did it post?"

Every status on the Dashboard comes from `task_label` / `target_label` in `views/dashboard.py` (they came from the Queue screen it replaced), never from `state.title()`. The numbers, charts and sections are in the root file under "The Dashboard replaced the Queue screen". The worker's own words told the user nothing ("Halted"), and two were wrong. Groups left behind by a stopped or cancelled batch said "Pending" for ever. A batch where every group was skipped said "Done" in green. A finished batch is named by what reached the groups: Posted, Posted to N of M, Nothing posted. A group that may have posted reads "Might have posted", and the note under it says to look at the group; it never reads "Not posted". A post of pictures that Facebook's reply did not confirm reads "Uploaded, not verified" (`unverified()`: done, no words, no `post_url`), never "Posted". Why a group was not posted is the note under it in Recent activity, under that group only. `tests/test_qtui_dashboard.py` (`TestTheLabels`, `TestRecentActivity`) pins it.

## Redrawing: an unchanged screen is not rebuilt

Every view used to clear its layout and rebuild every widget on every visit. Measured with 12 groups and 25 batches: **Queue 110ms, Groups 44ms, Publish 34ms** per view switch: all of it widget construction, to draw exactly what was already on screen. The Queue paid it again on *every worker event*, so during a batch, which is when someone is actually watching it, it rebuilt several times a minute.

Each of those four now computes a cheap **snapshot of what it would draw** (ids, states, labels, errors, selection) compares it with what is drawn, and returns early when they match. The result: **Queue 2.1ms, Groups 0.6ms, Publish 0.8ms, Compose 1.2ms.**

- **The snapshot must contain everything the widgets show.** Anything left out goes stale on screen and no test will catch it, because the data is right and only the pixels are wrong. `queue._snapshot` covers task state, error, body, scheduled time, schedule name, and every target's state, error and group name; `groups._snapshot` covers the label (name, or the looking-up placeholder) and tick.
- **Re-read, but in bulk.** These snapshots re-read the same rows the rebuild would have read rather than remembering them, because a stale read is a wrong screen. That still holds: but *one query per row* does not scale, and the Queue proved it: 25 batches x 6 targets took ~175 queries per refresh, because `_group_name()` looked up each target's group to recompute `t.group_label`, a string `targets_for` had already joined onto the row. `targets_for_tasks()` and `names_by_id()` fetch the whole screen in three queries. Same rows, same moment, nothing kept between refreshes, just not a round trip each.
- **Anything outside the guard still runs every time.** Publish's snippet reads the post body, which changes without the recipient list changing at all, so it is deliberately above the early return. Groups still calls `refresh_count()`, because Compose listens to it for its wording tabs.
- **The Queue kept a snapshot per card, not just per screen** (the Dashboard keeps one per list, for the same reason). One screen-wide snapshot answers "has anything changed", and during a batch the answer is yes on every worker event (one target moved to `done`), so all 25 cards were rebuilt for it, 127ms on the drawing thread, several times a minute, at exactly the moment someone is watching. `_cards_shown` holds each card's own row; when the batches are the same and in the same order, only the cards whose row moved are swapped out, through `widgets.replace_at`. Measured: **127ms -> 6.5ms** for a worker event. A card renders one batch, so this is safe in both scopes: Recent and All draw the same batch identically.
- `refresh(force=True)` rebuilds regardless, for a repaint the data cannot describe. So does anything that changes the list's length or order, since a reused card would then be sitting in the wrong row.
- **Widget state the user can change by clicking is not cache-able at all, and must be restated outside the guard.** The Compose wording tabs are `setCheckable` and in no exclusive `QButtonGroup`, so Qt flips the clicked button *before* `select_tab` runs. Three ways that broke, none of which alters a single label, which is what the guard is keyed on, so none of them could be fixed by widening the key: switching tabs left the highlight on the tab just left; clicking a second tab lit **two at once**; clicking the tab you were already on toggled it **off**, lighting none. The old unconditional rebuild corrected the fill every time and hid all three. `_mark_active_tab()` now restates `setChecked` after the guard, always. This is the general trap: a snapshot describes *data*, and a widget the user can mutate directly is not described by it.

**Nothing slow may run on the thread drawing the window.** `chrome.probe()` is a synchronous HTTP call to the debug port: ~14ms when Chrome answers, and up to `PROBE_TIMEOUT_S` (**one full second**) of a frozen window when something holds the port without replying. The Groups screen ran it inline on every show; it now runs inside the `run_in_background` worker, where the guard still applies. `tests/test_qtui_performance.py` pins that it stays there.

## The Compose preview is shaped like a real post

`PostPreview` in `qtui/views/compose.py` is deliberately built to look like a feed post: monogram avatar, name, meta line, text, **full-bleed** media, then a Like/Comment/Share row. That is not decoration: a preview that looks nothing like the destination cannot answer "will this read well when it lands?", which is the only question it exists to answer.

- **Pictures crop to fill their tile (`cover()`), they do not fit inside it.** Fitting leaves letterbox bars and makes a row of tiles look ragged; stretching distorts faces. The exception is a **single** picture, which keeps its natural aspect ratio (cropping the only photo in a post would misrepresent it) capped at `MAX_SINGLE_HEIGHT` so it cannot push the rest off screen.
- **Layouts are 1 / 2 / 3 / 4 / "+N"**, matching what a feed does. Past `MAX_TILES` the fourth tile carries a `+N` scrim.
- **A picture that will not open still gets a tile**, named, occupying its slot so the grid keeps its shape. The file is still going to be uploaded; showing nothing would suggest it had been dropped.
- **Short text with no picture is set large**, as a feed does. It is most of why the thing reads as a post rather than a label.
- **Preview mode gets the whole window.** The right rail (templates, "Sending to") and the attach button with its file list are all *writing* tools, and holding a third of the window plus 150px of height for them left the preview itself in half a screen, clipped, with its Like/Comment/Share row below the fold. `set_mode` stands both down, and the post is **centred** in the space the way a feed centres its column. Pinned to the left edge of a wide pane it read as a stray panel. Listing the attachments under a preview that already shows them was a second telling of the same fact, and it was the height that stopped the post fitting.
- **The canvas gets the full width; the post does not.** `MAX_POST_WIDTH` stays feed-shaped (500px, about what Facebook uses). Stretching the post to fill a wide window would defeat the only question the preview exists to answer.
- **The post width is recomputed on resize** (`post_width()`, clamped to `MIN_POST_WIDTH..MAX_POST_WIDTH`) rather than fixed, so a narrow pane never produces a horizontal scrollbar. `resizeEvent` only redraws past `RESIZE_SLACK`.
- **A picture is decoded at the size it is drawn, and only once.** `QPixmap(str(path))` decodes every pixel in the file. The user's own attachment is a 5712x4284 phone photo and takes **~600ms**, and the preview paid that *twice* per render (once in `_single_height`, merely to read the aspect ratio, and once to build the tile), then paid the pair again on every redraw, which includes a resize, the switch into Preview, and walking to another screen and back. Loading a template, switching to Preview and stepping to Groups and back measured **1137ms**; it is now **77ms**. `load_tile()` hands `QImageReader` the box it is filling so the JPEG decoder scales while decoding, and caches the result against the file's mtime and size; `image_size()` reads the header rather than decoding at all. **Never call `QPixmap` on an attachment path again**. That one line is worth more than every other redraw guard in this file put together.
- **The EXIF rotation is applied, because Facebook applies it.** A phone stores a portrait photo sideways with "rotate 90" in the header, so the preview used to show it on its side, and, worse, laid it out with the width and height the wrong way round, since `QImageReader.size()` reports the *stored* shape. `_oriented_size()` swaps the axes for the quarter-turn cases, and `setScaledSize` takes the stored orientation, so the target is swapped back before it is set. A preview that shows a photo in a different orientation to the destination is not answering the question it exists to answer.
- **The footer has no counts.** Inventing "12 likes" on a post that has not been published would be showing the user something untrue.
- **`text_shown()` still returns the logical post**, whatever the labels hold.

**Remove a widget with `widgets.clear()` or `widgets.replace_at()`, never by hand.** `takeAt()` does not unparent: the widget stays a child, goes on painting, and (no longer managed by any layout) reverts to Qt's **default 640x480**, so it paints at a size it never had. `clear()` calls `setParent(None)` as well, and recurses into nested layouts; `replace_at()` does the same for one widget, and is how the Queue swaps a single card. Both live in `widgets.py` because `tests/test_qtui_polish.py` fails on a `takeAt` anywhere in the views, so a new removal goes in that module, not in the view that needs it.

This was fixed once for the preview collage and then not applied to the five other places doing the same thing, which is how the Compose screen shipped with a **blue band across it**: the stale "All groups" tab was checked, therefore filled with the accent colour, and it painted 640x480 behind the tab strip, clipped by the scroll area into a neat rectangle that looked completely deliberate. Same root cause as the "duplicate row" and "stale collage" scares. `tests/test_qtui_polish.py` greps for a stray `takeAt` in the views so the sixth one cannot be written.

**A Qt flag enum is not an `int`, and the "never raise" wrapper will hide it.** `int(reader.transformation())` raises `TypeError` on PySide6. Use `.value`. That matters here beyond the typo, because image loading is deliberately wrapped so a corrupt attachment cannot take the screen down: the exception was swallowed and *every* picture silently became a named "no preview" tile. A rule that says "must never raise" needs its failure path checked against a file that is known to be good, or a programming error inside it looks exactly like a bad file.

## Visual rules, and the tests that hold them

`tests/test_qtui_theme.py` computes real WCAG ratios against both palettes rather than trusting that colours "look fine". It found five genuine failures in the inherited Facebook palette, so the values are no longer Facebook's:

- **`ACCENT` is `#0C68DE`, not `#1877F2`.** Facebook's own blue puts white text at 4.23:1, under the 4.5:1 floor. `WARNING` and `NEUTRAL` were moved for the same reason: `NEUTRAL` was the connection pill at 3.3:1.
- **`ACCENT_TEXT` is a separate token from `ACCENT`.** In dark mode the two have opposite requirements: the fill must be dark enough to carry white text, the text must be light enough to sit on a dark surface. One value cannot do both. Use `ACCENT` for fills and borders, `ACCENT_TEXT` anywhere the accent *is* the text.
- **Focus must stay visible.** A custom stylesheet replaces the platform focus rectangle, so `:focus` rules are load-bearing rather than decoration, without them, tabbing moves an invisible cursor. Never add `outline: none`; a test greps for it.
- **Exactly one accent-filled `#Primary` button per screen: the next step in the flow.** Compose and Groups each carried three (the step button, a secondary action beside it, and "Check connection", which sits in the sidebar on *every* screen), so the fill meant nothing anywhere. "Attach images", "Get my groups from Facebook" and "Check connection" are all plain buttons now; the accent belongs to "Next: …" and to "Post now". A checked `#Tab` (a Compose wording tab) is tinted and outlined in the accent, not filled with it, and a joined toggle raises its chosen segment in white: neither competes with the one filled button. Pinned by `tests/test_qtui_polish.py`.
- **A bare container inside a card paints the window background.** `QLabel`, `QCheckBox`, `QWidget#Row` and **`QStackedWidget`** are all listed transparent in the stylesheet; the last was missing, and the Publish mode switcher drew a grey slab across the white "When" card wherever its page did not cover it. Anything new that holds children inside a card goes on that list.
- **The checkbox indicator is styled explicitly, in both states.** Left to the platform, checked drew a bare grey tick with no box and unchecked drew an empty box: two states that did not look like one control, with *selected* the fainter of them, on the one screen whose whole job is picking groups. It is now an accent-filled rounded box with a white tick from `qtui/assets/check.svg`. The path is fed through `Path.as_posix()`: **a backslash is an escape character inside a Qt stylesheet**, so a native Windows path loads nothing and fails silently. If the SVG ever goes missing the box still fills with the accent, so the state stays readable and only the tick is lost.
- **The action sits with what it acts on.** Publish put `addStretch(1)` above its summary and Post button, anchoring them to the bottom of the window; in Now and Once modes, where the panel is one line, that left a void most of the screen tall between choosing and doing. The slack goes below everything.
- **Body text is 15px and the application font sets family only.** It used to be 13px *and* shrunk another 2pt by `QFont(FONT_FAMILY, SIZE_BODY - 2)` in `run()`: two sources of truth for size, with the smaller one winning.

- **`DANGER` is `#C0283C`, not `#D32F45`.** The old red read 4.39:1 on the window colour, which is where every error toast is written, and no test checked that pair. It also could not sit on any tint, and the destructive `#Link` buttons now gain one on hover.

## Controls: a click has to land, and has to show that it did

Reported as "the up and down buttons on the time are partially working or not working at all". Both halves were true, for two unrelated reasons. The time fields have since become lists (see "Times are picked from two lists" above), and the Settings number boxes went with the posting rules (2026-10-18). No screen has a number box now, but the stepper styling is still in the stylesheet for the next one, and `tests/test_qtui_controls.py` pins it against a plain spin box.

- **A stylesheet spin box must reserve room for its buttons in `padding-right`.** The text box inside a `QAbstractSpinBox` is sized from the stylesheet's padding, which knows nothing about the step buttons. With plain `padding: 8px` it lay across the left half of "up", and clicks there went into the text. `STEPPER_ROOM` / `DROPDOWN_ROOM` in `theme.py` are that room, and the step buttons are drawn by the stylesheet: side by side, nearly full height, like the Windows 11 number box. The test hit-tests real geometry under the real stylesheet. Calling `stepBy()` can never find this bug.
- **Every field that decides when or how often a post goes out ignores the mouse wheel.** That's `DateEntry` and every `TimeList` (and was the Settings number boxes, until they went). A `QComboBox` changes its choice on the wheel by default, which is why `TimeList` overrides it. The cooldown was the quiet one: there was one per row of a scrolling list, so scrolling the list changed a cooldown on every row it passed.
- **`widgets.AppStyle` does what a stylesheet cannot, once, for every widget as Qt polishes it**, including rows rebuilt later. It gives a hand cursor to buttons and drop-downs. It also sets **Tab-only focus on buttons**: with click focus, the focus ring stayed on whatever had been clicked last, and a clicked group's name turned bold blue. `run()` installs it *before* `setStyleSheet`, because the stylesheet wraps whatever style is installed when it is set.
- **Because a click no longer takes focus from a field, it no longer commits what was typed there.** Losing focus is what makes Qt read a half-typed value. Anything that *acts* on typed values calls `interpretText()` first: see `PublishView.commit_typed_times()`, which now has only the one-off day left to commit. Never call it from a per-keystroke path such as `refresh_summary()`. Interpreting mid-typing finishes a field for the user after its first digit.
- **`:pressed` rules come after `:focus` rules** in the stylesheet. Both are true during a keyboard press, and the later rule wins.
- **Icons are per mode, and per state for the steppers.** An SVG cannot take its colour from the palette, so each arrow exists as `chevron-<dir>-<light|dark>[-off].svg`. Name it in `theme.ICON_NAMES` and reference it through `theme.icon()`. A test checks that every `url()` in both stylesheets exists, and `--selftest` checks the set in the bundle.
- **A `QComboBox` ignores `::item` rules until it has a `QStyledItemDelegate`.**
- **App-wide spin-box rules reach spin boxes Qt builds for itself.** The calendar's year box is one: sized from its hint, it took the stepper padding, ran off the calendar's edge and covered the next-month arrow. `QCalendarWidget QSpinBox` restyles it compact and buttonless. Test it the way a user reaches it, by clicking `qt_calendar_yearbutton`. Showing the year box by hand renders it unlaid-out, and that produced a convincing but wrong diagnosis.
- **The calendar marks an out-of-range day only with the palette's window colour as its background**, which a one-colour calendar hides. `DateEntry.dim_past_days` greys the past explicitly. Days of the neighbouring months are drawn in the palette's *disabled* text colour, which is what `QCalendarWidget QAbstractItemView:disabled` sets. Remove that rule and they turn as dark as the month on show.

Measured click-to-settled times, best of five: most buttons take 1-20ms. Switching Now/Once/Repeat and the Compose Preview toggle cost 10-45ms, and the time is Qt laying out the page it reveals, not our code. The code before these changes measured the same.

**`WA_DontShowOnScreen` cannot show a `QPushButton` in its `:hover` state**, though checkboxes and spin boxes do show it there. Use `setDown(True)` to render `:pressed`. Absent hover in such a screenshot proves nothing, just as with focus below.

**Verifying focus states is not possible through the normal render harness.** `WA_DontShowOnScreen` windows are never active, so `hasFocus()` is False and `:focus` never fires. An absent ring in such a screenshot proves nothing. Use the `offscreen` *platform plugin* instead (`QT_QPA_PLATFORM=offscreen`), where windows do activate; text renders as tofu there because the platform has no fonts, but borders draw correctly.
